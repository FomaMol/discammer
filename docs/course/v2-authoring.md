# Course lesson contract v2

A normal lesson keeps its existing `{module}/{slug}.{en|ru}.json` filename, `order`, title and `body_md`. The Markdown body is the substantial explanation, with mechanisms and limits. For v2 set `widget_type` to `course_v2` and put the following authored fields in `widget_config`:

- `version: 2`, a stable `revision` such as `2026-10-20`, `goal`, `today_action`, `checked_at` (ISO date), `scope` (where and when advice applies), and `sources` with public HTTPS `title`, `url`, `scope`. Change `revision` when the taught content is substantially revised again.
- `blocks` in reading order: at least two `case` blocks, exactly one `practice` block, exactly one `check` block. One case must be a legitimate but confusing situation. All examples are synthetic unless precisely sourced and labeled otherwise.
- A `case` has `title`, `situation`, `analysis`, `legitimate` boolean.
- A `practice` has `title`, `setup`, `synthetic: true`, `steps` (3–7), `debrief`, and `mode: "sequence"` or `"graph"` (`sequence` is the default). Each step has a `prompt` and at least two `choices`. Each choice has `text`, `consequence`, `explanation`, and a real `recommended` boolean; exactly one is recommended per step. In sequence mode, every choice proceeds to the next listed decision, and the final choice ends the exercise. In graph mode, each step also has a unique slug `id`, and every choice has `next` set to another step ID or `"end"`. The graph must be acyclic, every step reachable, and every possible route must contain at least three decisions. Use graph mode where a dialogue or incident actually changes after a choice; use sequence mode for ordered checks/settings where the next task stays the same. A learner can retry a decision, read the consequence, see a route debrief, and replay.

Read every reachable choice route as a continuous story. A later prompt, consequence, or debrief must not assume a verification, payment, disclosure, or recovery action the learner did not take; explicitly introduce a fresh independent checkpoint when that is the intended design. Vary the positions of recommended practice choices and correct transfer answers across each module and preserve those positions between EN and RU. The renderer displays authored order. A fixed answer position lets a learner pass without using the taught skill.
- A `check` has `title` and 3–5 `questions`. Each question has `prompt` and two or more `choices`; each choice has `text`, `explanation`, `correct` boolean, with exactly one correct. These test transfer rather than repeat the practice.

Use natural authored EN and RU with equivalent facts, actions and answer keys. Source links remain the same across locales; source titles/scope are localized. A paired loader checks structural and answer parity; human reviewers check meaning. The server renders all blocks as a readable static fallback with decisions and explanations in disclosure controls. The browser enhances practice and checks without sending answers or user input to the server. Earlier slug-based lesson completion remains intact; v2 adds a separate local completion entry keyed by module, slug and authored revision, included in export/import and encrypted sync. An earlier completion is never silently relabeled as completion of the revised practice. Legacy `quiz`, `scenario`, `redflags`, `exam`, and `certificate` remain accepted. The final exam and local completion record use their existing widget contracts while their instructional text and assessment content are revised separately.

For a substantially revised legacy exam, add the same stable `revision` to both exam widget configs. The exam stores that result separately from the old unversioned result. Give the paired completion-record configs that `revision` and `examRevision`; the record checks the current revision of each required lesson and the matching revised exam. Old lesson and exam records remain available in the export/import and encrypted sync dossier, but do not count as completion of the revised course. The lesson-summary and manifest APIs expose only revision identifiers, never user progress.

`backend/course_contract.py` rejects incomplete v2 lessons during local load/seed. Run backend tests, frontend tests and build, the i18n audit, and inspect both locale routes with JavaScript on and off. Never change generated assets manually.
