## 1. Задача и границы

**Что решаем.** Слабое место W10: прогресс курса, результат экзамена и имя для
сертификата живут только в `localStorage` и исчезают при очистке браузера или смене
устройства.

**Что даём.** Опциональную синхронизацию через **sync-код**: прогресс шифруется на
клиенте, сервер хранит только шифротекст и не может его прочитать. Без email, без
паролей, без PII на сервере.

**Решения владельца (2026-07-15), зафиксированные до дизайна:**

| Вопрос | Решение |
| --- | --- |
| Модель | Вариант A (sync-код), не magic-link по email |
| Формат кода | Генерируемый клиентом, 128 бит |
| Хранение | TTL 12 месяцев, продление при обращении |
| Отправка | Авто-push с дебаунсом после явного opt-in |

**Не-цели (YAGNI).** Аккаунты, логин, восстановление кода, шеринг прогресса между
людьми, серверный рендер прогресса, история версий блоба, разрешение конфликтов
сложнее уже существующего best-of merge.

## 2. Ключевое наблюдение: payload уже написан

`frontend/src/utils/progress.ts` уже экспортирует ровно то, что нужно синхронизировать:

- `exportProgress(): Dossier` (строка 264) — собирает четыре долговечных ключа;
- `importProgress(json): ImportOk | ImportErr` (строка 290) — **недеструктивный
  best-of merge**: объединение уроков, лучший результат экзамена по соотношению,
  `passed` через OR, подтверждённое имя сертификата не перетирается, лучший результат
  по каждому гайду. Не бросает исключений, не мутирует состояние при отказе, отвергает
  `not-json` / `not-an-object` / `unsupported-version` / `bad-lessons` / `bad-exams` /
  `bad-guidechecks`. Покрыт `progress.test.ts`.

```ts
export interface Dossier {
  v: number;            // DOSSIER_VERSION = 2, импортёр принимает v ∈ [1, 2]
  exportedAt: string;
  lessons: ProgressShape['modules'];
  exams: ExamRecord | null;
  certName: string | null;
  guideChecks: GuideChecks;
}
```

**Следствие:** семантику слияния проектировать не нужно — она есть и протестирована.
Синк сводится к транспорту:

```
push: JSON.stringify(exportProgress())  → encrypt → POST
pull: POST → decrypt → importProgress(plaintext)
```

Синхронизируются четыре ключа: `discammer:progress:v1`, `discammer:exam:v1`,
`discammer:certificate:name`, `discammer:guidechecks:v1`.
`discammer:course:briefing-typed:v1` — **не** синхронизируется: это `sessionStorage`
и UI-флаг проигранного typewriter'а, не прогресс.

## 3. Модель угроз

Сервер хранит шифротекст под `blob_id`, выведенным из кода. Отсюда:

1. **Любой может перебирать `blob_id` и выкачивать блобы.** Значит блоб обязан быть
   бесполезен без кода → шифрование на клиенте обязательно, а не «для галочки».
2. **Брутфорс идёт офлайн.** Скачал блоб — перебирай сколько хочешь, rate-limit не
   мешает. Значит **энтропия кода — единственная реальная защита**.
3. **`blob_id` — не секрет, но и не публичен.** Он не даёт расшифровать блоб, но даёт
   право его скачать и удалить. Следовательно `blob_id` не должен попадать в
   access-логи → **id передаётся в теле POST, а не в URL**.
4. **Сервер враждебен по предположению.** Дизайн обязан оставаться корректным, даже
   если БД утекла целиком.

Ответ на (2): код 128-битный и генерируется машиной, а не человеком. Поэтому медленный
KDF не нужен — он жёг бы CPU на 2-ядерном VPS, ничего не добавляя: перебор 2¹²⁸
нереален при любом KDF.

### Что остаётся вне защиты (честно)

- **Потеря кода = безвозвратная потеря блоба.** Восстановления нет и не может быть:
  сервер не знает, кому принадлежит блоб. Это прямое следствие «без email», и UI обязан
  предупредить об этом до генерации, а не после.
- **Утечка кода = утечка прогресса** тому, кто им завладел.
- Сервер видит метаданные: факт обращения, IP, размер блоба, время. Не видит содержимое.

## 4. Криптография

Ноль новых зависимостей: голый WebCrypto. В `frontend/package.json` сейчас только
`plyr`, `plyr-react`, `react`, `react-dom` — крипто-библиотек нет, и не появится.

### 4.1 Sync-код

```
secret = crypto.getRandomValues(new Uint8Array(16))    // 128 бит
code   = crockfordBase32(secret)                        // 26 символов
```

**Crockford base32**, а не стандартный RFC 4648: исключены `I`, `L`, `O`, `U` —
их путают при переписывании с экрана на экран, а это ровно наш сценарий. Ввод
регистронезависим, при разборе `I`/`L` → `1`, `O` → `0`.

Показывается группами с префиксом-маркером:

```
DSCM-K7F2Q-9MXV3-8HTRB-4WNJ0-C5ZY
```

Префикс `DSCM` — не данные; он не парсится, а только помогает человеку опознать
строку. При вводе отбрасывается вместе с дефисами и пробелами.

### 4.2 Разделение ключей

Из одного секрета выводятся два **независимых** ключа через HKDF-SHA256:

```
blob_id  = HKDF-SHA256(ikm=secret, salt="discammer-sync-v1", info="id",  len=32) → hex
enc_key  = HKDF-SHA256(ikm=secret, salt="discammer-sync-v1", info="enc", len=32) → AES-GCM
```

HKDF-Expand — это PRF на HMAC, поэтому знание `blob_id` не даёт ни `secret`, ни
`enc_key`. Сервер видит только `blob_id`.

Медленный KDF (PBKDF2/Argon2) сознательно **не применяется**: IKM равномерно случаен и
имеет полные 128 бит. Растягивание защищает от слабой энтропии, которой здесь нет.

### 4.3 Шифрование

```
iv   = crypto.getRandomValues(new Uint8Array(12))       // свежий на КАЖДЫЙ push
ct   = AES-GCM-256(key=enc_key, iv, plaintext=JSON.stringify(exportProgress()))
blob = base64(iv || ct)
```

IV переиспользовать нельзя: повтор пары (key, iv) в GCM ломает конфиденциальность и
аутентичность. GCM даёт AEAD, поэтому подмена шифротекста сервером обнаруживается при
расшифровке — обрабатывается как «блоб повреждён», а не как молчаливый провал.

### 4.4 Доступность WebCrypto

`crypto.subtle` требует secure context (HTTPS или localhost) и в проекте сейчас не
используется нигде. Нужен фича-детект и **тихая деградация** — прячем UI синка целиком,
в стиле уже принятых в проекте конвенций молчаливого вырождения. Курс без синка обязан
работать ровно как сегодня.

## 5. Сервер

### 5.1 Схема

```sql
CREATE TABLE IF NOT EXISTS sync_blob (
  blob_id      TEXT PRIMARY KEY,
  ciphertext   BLOB NOT NULL,
  updated_at   TEXT NOT NULL,
  last_seen_at TEXT NOT NULL
);
```

Добавляется в `SQL_CREATE_TABLES` (`backend/database.py:11-75`).

### 5.2 Выживание при reseed — главный инвариант

В проекте **две** деструктивные ветки, и обе — хардкод-аллоулисты на четыре контентные
таблицы:

1. `seed_data.py:1064-1075` — `DELETE FROM post/scam_guide/course_module/lesson`
   (+ `sqlite_sequence` по тем же именам);
2. `database.py:171-182` — `DROP TABLE` при дрейфе колонок, итерирует кортеж из четырёх
   записей `_*_REQUIRED_COLS`.

`sync_blob` исключается из обеих **тем, что мы её туда не добавляем**. Это ровно тот
контракт, который уже обещан в докстринге `seed_data.py:1025-1029`:

> «Future user-state tables (e.g. course progress) MUST live in separate tables so this
> wipe never touches them.»

**Запрет:** не вносить `sync_blob` в `_*_REQUIRED_COLS` — там стратегия drop-based, и
для пользовательского состояния она недопустима. Системы миграций в проекте нет;
эволюция схемы сегодня — «drop and reseed», что для этой таблицы применять нельзя.
Изменение схемы `sync_blob` в будущем потребует отдельного решения.

`SEED_ON_STARTUP=0` (`config.py:24`) на путь не влияет — таблица не в списках в обоих
режимах.

### 5.3 Эндпоинты

Все три — **POST с `blob_id` в теле**, не в URL. Причина в §3.3: путь попал бы в
access-логи nginx. Побочно это решает и вторую проблему: exempt-set рейт-лимитера
(`main.py:111-113`) сверяется по точному совпадению пути, поэтому параметризованный
маршрут вида `/api/sync/{id}` в него не попал бы.

| Метод | Путь | Тело | Ответ |
| --- | --- | --- | --- |
| POST | `/api/sync/push` | `{blob_id, blob}` | `204` |
| POST | `/api/sync/pull` | `{blob_id}` | `200 {blob, updated_at}` · `404` если нет |
| POST | `/api/sync/delete` | `{blob_id}` | `204` (идемпотентно) |

`delete` существует ради data-minimization: пользователь должен уметь стереть свои
данные с сервера, а не только перестать их слать.

Живут в `backend/main.py` рядом с `/api/client-errors` и `/api/csp-report` — оба
существующих POST'а там, а `routers/api.py` содержит только GET'ы. Это осознанно:
паттерн `/api/client-errors` (`main.py:593-640`) — кап тела **до** разбора
(`Content-Length` → 413, затем стриминговый кап, чтобы подделанный/отсутствующий
Content-Length не заставил буферизовать без предела) — здесь нужен один в один.

**Кап тела:** 64 KB. `Dossier` — единицы килобайт (9 модулей × уроки + экзамен + имя +
чек-листы гайдов), так что 64 KB это запас, а не ограничение.

**Валидация `blob_id`:** строго 64 hex-символа. Всё остальное — 400, до любого касания
БД.

### 5.4 Рейт-лимит

Свой бакет по образцу beacon'а: `SYNC_RATE_LIMIT` в `config.py` (дефолт 20/мин),
`_sync_limiter = RateLimiter(SYNC_RATE_LIMIT)` в `main.py`, три пути в
`_API_RATE_LIMIT_EXEMPT` (чтобы не считаться дважды с общим лимитом 240/мин), вызов
`.allow(_client_ip(request))` внутри хендлеров.

**Обязательно:** добавить `_sync_limiter` в кортеж autouse-фикстуры
`_reset_rate_limiters` (`backend/tests/conftest.py:41`). Фикстура `client` session-scoped
и TestClient всегда приходит с одного peer IP `testclient`, поэтому без сброса счётчики
протекут между тестами и суита начнёт мигать.

### 5.5 Ретенция

TTL **12 месяцев** по `last_seen_at`; каждый push и pull его продлевает. Свип:

```sql
DELETE FROM sync_blob WHERE last_seen_at < :cutoff
```

Два триггера: (1) на старте в `lifespan` — уже сериализован через flock, дёшево;
(2) интервально-гейтед свип внутри `push`, не чаще раза в сутки — старта одного мало
для долгоживущего процесса.

Активный пользователь не теряет ничего никогда; курс из 9 модулей реально проходят за
недели, не за годы.

## 6. Клиент

### 6.1 Модули

| Файл | Роль |
| --- | --- |
| `frontend/src/utils/sync.ts` | код ⇄ секрет (Crockford base32), HKDF-разделение, AES-GCM, транспорт |
| `frontend/src/components/ProgressSync.tsx` | остров UI |

Регистрация — 24-я запись в `components` (`frontend/src/main.tsx:17-41`), лениво, как
все остальные. Монтирование — на `course.html`, рядом с `CourseProgress`
(`course.html:127`), то есть рядом с тем прогрессом, который синк и синхронизирует.

`ProgressSync` получает `data-props='{"locale":"{{ _lang }}"}'` — инлайновый JSON, как
у `CourseProgress` (конвенция для тривиальных пропсов).

Состояние связки (сам код) хранится в `localStorage` под новым ключом
`discammer:sync:v1`. **Этот ключ не входит в `Dossier`** и не синхронизируется — иначе
код уехал бы внутрь собственного шифротекста.

### 6.2 Состояния UI

**Не связан.** Объяснение + две ветки: «Создать код» и «Ввести существующий».
При создании — код показывается **один раз крупно**, с копированием и скачиванием, и с
честным предупреждением: *код потерян → прогресс потерян, восстановления нет*.
Предупреждение обязано быть **до** генерации и рядом с кодом, а не в мелком тексте.

**Связан.** Замаскированный код (первая и последняя группы), время последнего push'а,
кнопки «Обновить с сервера», «Отвязать» (локально) и «Удалить с сервера» (стереть
блоб). Отвязка и удаление — разные вещи, и UI обязан их различать.

**Авто-push.** После opt-in — дебаунс ~2 с на события `subscribe()`
(`progress.ts:75`, события `discammer:progress` / `discammer:exam` /
`discammer:guidechecks`). Синхронизация без авто-push не закрывает W10: человек не
вспоминает про кнопку «сохранить» до того, как почистит браузер.

Ошибка сети при авто-push не должна ломать урок: тихий retry, видимый статус, никаких
блокирующих модалок.

**Pull.** Ввод кода → `pull` → расшифровка → `importProgress()` мержит.
Merge недеструктивный, поэтому «затирания» локального прогресса чужим кодом не
происходит by construction.

### 6.3 Service worker

PERF-3 SW (`frontend/sw-src.js`) обязан обходить `/api/sync/*` — кэшировать их нельзя
ни в каком виде. Проверить и, если нужно, явно исключить.

### 6.4 i18n

Все строки — парой EN/RU, `.venv/bin/python scripts/i18n_audit.py` зелёный.
Код языконезависим (base32), поэтому переносится между локалями без сюрпризов — это
одна из причин, по которой словарные фразы были отвергнуты.

## 7. Влияние на приватность и клеймы

**Чекер и инспектор не затрагиваются вообще.** Это другая подсистема; гарантия «текст
не покидает браузер» и e2e `assertNoNetworkLeak` остаются в силе без изменений. UX-4 не
имеет к ним отношения, и в спеке это должно быть сказано прямо, чтобы никто не
«обобщил» синк на инструменты.

**Но клейм про прогресс меняется, и это надо признать честно.** Сегодня публично
утверждается, что прогресс browser-local. После UX-4 корректная формулировка:

> прогресс локален по умолчанию; опциональная синхронизация хранит на сервере только
> клиент-шифрованные данные, которые сервер не может прочитать.

**`certName` — это введённое пользователем имя, то есть PII.** Оно шифруется на клиенте
и сервер его прочитать не может, но утверждение «на сервере нет PII» корректно **только
потому, что** данные зашифрованы, а не потому, что имени там нет. Формулировать надо
именно так — «сервер хранит шифротекст», а не «мы не собираем имя».

Правки в `docs/portfolio/CLAIM_LEDGER.md` — часть реализации, а не то, что делается после неё.

**Первая writable-таблица проекта.** REL-1 (`scripts/backup-db.sh`) бэкапит БД целиком,
так что `sync_blob` покрыт автоматически — но `docs/ops/backups.md` и
`docs/ops/runbook.md` до сих пор описывают БД как «пересевается из git», и это перестаёт
быть правдой. Обновить: RPO/RTO теперь имеют смысл, потеря БД теперь теряет
пользовательские данные.

## 8. Тесты

**Инвариант №1 — reseed не трогает `sync_blob`.** Место: `backend/tests/test_db_lifecycle.py`,
рядом с `test_seed_on_startup_off_skips_wipe`. Записать блоб → выполнить
`seed_database()` → блоб на месте. Это тест на обещание из докстринга; без него UX-4
нельзя считать сделанным. Отдельно — что дрейф-детектор не дропает таблицу.

**Backend:**
- round-trip push → pull → совпадение байт;
- pull несуществующего `blob_id` → 404;
- delete идемпотентен; delete → pull → 404;
- тело > 64 KB → 413 (и по `Content-Length`, и потоком без него);
- превышение лимита → 429;
- кривой `blob_id` (не 64 hex) → 400;
- **в БД нет плейнтекста**: записать блоб с известным маркером в открытом тексте,
  прогрепать файл БД — маркера нет;
- свип удаляет просроченное и не трогает свежее.

**Frontend (vitest):**
- Crockford base32 round-trip; регистронезависимость; `I`/`L`→`1`, `O`→`0`;
- HKDF даёт разные `blob_id` и `enc_key` из одного секрета, и обе величины
  детерминированы;
- AES-GCM round-trip; порча шифротекста → отказ расшифровки (а не мусор);
- фича-детект отсутствия `crypto.subtle` → UI скрыт, курс работает.

**e2e:** прогресс переезжает между двумя чистыми контекстами браузера по коду.
Плюс — не ослаблен ли `assertNoNetworkLeak` для чекера/инспектора.

## 9. Риски

| Риск | Митигация |
| --- | --- |
| Пользователь теряет код и винит продукт | Предупреждение до генерации, копирование + скачивание, повтор при связке |
| Авто-push шлёт данные, которых человек не ждёт | Явный opt-in; до связки — ноль сетевых запросов; статус виден |
| `sync_blob` попадёт под будущий wipe | Тест-инвариант §8 №1 + докстринг + запрет на `_*_REQUIRED_COLS` |
| Нет миграций для user-таблицы | Признано в §5.2; изменение схемы — отдельное решение |
| Рост таблицы | TTL 12 мес. + свип |
| Новый лимитер протечёт в тестах | `conftest.py:41` — обязательный пункт |
| Первый реальный write-путь на WAL | БД уже WAL + `busy_timeout=5000`; нагрузка синка ничтожна |
